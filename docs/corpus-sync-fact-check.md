# Verdict List

**1. Fresh listen (no resume token) bills one read per doc in the initial result set — CONFIRMED.**
The pricing docs: "When you listen to the results of a query, you are charged for a read each time a document in the result set is added or updated" — the entire initial result set counts as "added" on first attach, and the realtime-queries doc describes the initial attach as a polling operation over the full result set. A fresh listen over 38k docs ≈ 38k billed reads. There is also a minimum charge of one read per query even if empty.
Sources: [Firestore pricing](https://firebase.google.com/docs/firestore/pricing), [Real-time queries at scale](https://firebase.google.com/docs/firestore/real-time_queries_at_scale)

**2. Persisted resume token means re-attach in a later session bills only deltas — PARTIALLY TRUE, and REFUTED for the typical "later session" case.**
The correct semantics, verbatim from the pricing page: "If offline persistence is enabled and the listener is disconnected for **more than 30 minutes**, you will be charged for documents and index entries read as if you had issued a **brand-new query**." So the resume token saves billing only when re-attach happens within ~30 minutes; a next-day session re-bills the full result set (bandwidth may still be delta, billing is not). Without persistence, every disconnect/reconnect bills as a brand-new query. "Same query" = same query target (identical canonical form: path, filters, orderBys, limits) — any shape change is a different target with no resume state (see issue #4501 on per-query-identity read sharing).
Sources: [Firestore pricing](https://firebase.google.com/docs/firestore/pricing), [firebase-js-sdk #4501](https://github.com/firebase/firebase-js-sdk/issues/4501), [firebase-js-sdk #3422](https://github.com/firebase/firebase-js-sdk/issues/3422)

**3. loadBundle() bills zero Firestore reads — CONFIRMED (with the intended usage caveat).**
The bundle is a static serialized file; the Firebase blog states clients read from CDN and then query "against that cached data… avoid making extra calls against the Firestore database," and advises `{source: 'cache'}` to guarantee no server reads. The reads are billed once, server-side, when the Admin SDK executes the queries at build time (per the Bundle Builder extension's billing notes). Loading the file itself touches no Firestore billing meter.
Sources: [Firestore data bundles blog](https://firebase.blog/posts/2021/04/firestore-supports-data-bundles/), [Bundles guide](https://firebase.google.com/docs/firestore/bundles), [Bundle Builder extension](https://firebase.google.com/docs/extensions/official/firestore-bundle-builder)

**4. onSnapshot on a bundle named query resumes from bundle readTime and bills only post-bundle deltas — PARTIALLY TRUE; the billing half is UNDOCUMENTED and likely WRONG for any bundle older than 30 minutes. SAY IT LOUDLY: do not build a cost model on this.**
The *mechanism* is real and I verified it in SDK source: `localStoreSaveNamedQuery` in `firebase-js-sdk/packages/firestore/src/local/local_store_impl.ts` allocates a target "such that it can be resumed from associated read time if users use it to listen," setting the target's snapshot version to the bundle readTime (`allocated.withResumeToken(ByteString.EMPTY_BYTE_STRING, readTime)`). So a listen on the named query resumes from the bundle snapshot and only *transfers* changed docs. But **no official doc anywhere states the listen is billed as deltas only** — and the documented 30-minute rule ("disconnected for more than 30 minutes… charged as if you had issued a brand-new query") applies squarely: a nightly bundle's readTime is hours old, so the first listen attach should be expected to bill the **full result set** even though wire traffic is delta. Bandwidth savings ≠ billing savings. No GitHub issue or doc contradicts this; treat "bundle + listener = cheap" as unproven at best.
Sources: [local_store_impl.ts](https://github.com/firebase/firebase-js-sdk/blob/main/packages/firestore/src/local/local_store_impl.ts), [Firestore pricing](https://firebase.google.com/docs/firestore/pricing)

**5. loadBundle merges; docs absent from the bundle are not removed locally — CONFIRMED.**
Bundle loading writes docs into the cache if newer and never tombstones cached docs missing from the bundle. A firebase-talk thread documents exactly this: a doc removed from the bundled query's results "still includes document 1 despite the bundle API returning without it" — named query results merge with cached data. Bundles cannot communicate deletions; you need out-of-band reconciliation.
Sources: [firebase-talk: Firestore bundles behaviour](https://groups.google.com/g/firebase-talk/c/CIEtfBjz5ok), [flutterfire #9564](https://github.com/firebase/flutterfire/issues/9564) (same cache semantics)

**6. count() bills 1 read per 1000 index entries and works in the client JS SDK — CONFIRMED.**
"You are charged one read operation for each batch of up to 1000 index entries read"; minimum 1 read for zero entries. 60k docs ≈ 60 reads. Available in the modular JS SDK as `getCountFromServer()` (since v9.11, present in v11/v12). Caveat: aggregations are server-only — they are not answered from the offline cache.
Sources: [Aggregation queries](https://firebase.google.com/docs/firestore/query-data/aggregation-queries), [Firestore pricing](https://firebase.google.com/docs/firestore/pricing)

**7. Free tier: 50k reads / 20k writes / 20k deletes per day, project-wide, all readers count — CONFIRMED.**
Google Cloud free-features page: "50,000 reads, 20,000 writes, and 20,000 deletes per day **per project**" (plus 1 GiB storage, 10 GiB/month egress). The quota is per project, not per client class — Admin SDK / Cloud Functions reads draw from the same daily pool. On exhaustion, operations fail with `RESOURCE_EXHAUSTED` until the daily reset around midnight Pacific. Note: free quota applies to a single (default) database per project.
Sources: [Free cloud features](https://docs.cloud.google.com/free/docs/free-cloud-features), [Firestore quotas](https://firebase.google.com/docs/firestore/quotas)

**8. Admin SDK builds bundles; docs recommend caching the built bundle — CONFIRMED.**
Node Admin SDK: `firestore.bundle(bundleId)` → `.add(...)` → `.build()` (BundleBuilder). The bundles guide's serving examples are Firebase Hosting with CDN caching (verifying `X-Cache` headers) and Cloud Storage; the official Bundle Builder extension likewise builds once and caches in Hosting CDN/Cloud Storage.
Sources: [Bundles guide](https://firebase.google.com/docs/firestore/bundles), [BundleBuilder API](https://googleapis.dev/nodejs/firestore/latest/BundleBuilder.html), [Bundle Builder extension](https://firebase.google.com/docs/extensions/official/firestore-bundle-builder)

**9. Worker persistence requires single-tab/force-ownership; multi-tab impossible in workers — CONFIRMED.**
Multi-tab coordination requires LocalStorage, which does not exist in workers ("IndexedDbPersistence LocalStorage is unavailable…"); in a dedicated worker the only working config is `persistentSingleTabManager({forceOwnership: true})` (legacy `experimentalForceOwningTab`). API docs on `forceOwnership`: it "will enable IndexedDB, but cause **other tabs using IndexedDB cache to fail**" — i.e., a second client contending for the same persistence DB gets `failed-precondition` errors on its persistence layer (two force-owners fight over the primary lease; behavior is "other tab breaks," not graceful sharing). Open FRs #8438/#7364 confirm this is still the state of the world.
Sources: [PersistentSingleTabManagerSettings](https://firebase.google.com/docs/reference/js/firestore_.persistentsingletabmanagersettings), [firebase-js-sdk #7364](https://github.com/firebase/firebase-js-sdk/issues/7364), [#8438](https://github.com/firebase/firebase-js-sdk/issues/8438), [#6962](https://github.com/firebase/firebase-js-sdk/issues/6962)

**10. `updated > ts` alone = automatic single-field index; adding `published == false` = composite index — CONFIRMED.**
Index-overview: single-field automatic indexes serve "simple queries based on field values and the comparators <, <=, ==, >=, >, in"; but "if you need to run a compound query that uses a range comparison… you must create a [composite] index" — the docs' own example is exactly equality-on-one-field + range-on-another. (Index merging only helps equality/array-contains combinations, not equality+range.)
Source: [Index types in Cloud Firestore](https://firebase.google.com/docs/firestore/query-data/index-overview)

**11. Hosting/Storage free tiers and function streaming limits — PARTIALLY TRUE with important corrections.**
Hosting no-cost: **10 GB storage, 10 GB/month data transfer** (the old 360 MB/day figure is obsolete; it's now monthly). At 50–200 MB per bundle, that's only ~50–200 free downloads/month. Cloud Storage always-free: 5 GB-months (us-east1/us-west1/us-central1 only), 5,000 Class A + 50,000 Class B ops/month, 100 GB/month North America egress per the free-features page — much roomier for egress, though note Cloud Storage *for Firebase* default buckets now require the Blaze plan for new projects (Oct 2024 change; see firebase.google.com/pricing). Streaming a large authed response through a function: **not viable at 50–200 MB** — Hosting rewrites impose a hard 60-second timeout regardless of function config, and functions cap responses at 10 MB (gen1), 32 MB non-streaming / 10 MB streaming (gen2). Serve big bundles as static Hosting assets or from GCS (signed URLs / Storage rules), not through functions.
Sources: [Hosting usage & quotas](https://firebase.google.com/docs/hosting/usage-quotas-pricing), [Free cloud features](https://docs.cloud.google.com/free/docs/free-cloud-features), [Hosting + Functions](https://firebase.google.com/docs/hosting/functions), [Cloud Run functions quotas](https://docs.cloud.google.com/functions/quotas)

**12. Per-changed-doc billing after attach; "1 read per 30 min of empty listen" — PARTIALLY TRUE / the idle-charge rumor is REFUTED.**
Confirmed rules: (a) one read per doc added/updated in the result set, plus one read when a doc leaves the result set due to a change; (b) minimum one read per query even if empty (applies at listen attach); (c) the only 30-minute rule is the *disconnect* rule from claim 2 — there is **no documented per-connection or per-30-minutes-of-idle-listening charge**. An attached, quiet listener costs nothing while connected.
Sources: [Firestore pricing](https://firebase.google.com/docs/firestore/pricing), [Billing report guide](https://docs.cloud.google.com/firestore/docs/billing-questions)

# Implications

The verdicts cut against any architecture that leans on **listener resume semantics for cheap boots**: claims 2 and 4 establish that resume tokens (whether from IndexedDB persistence or a bundle's readTime) buy delta *bandwidth* but not delta *billing* once the gap exceeds 30 minutes — so both "re-attach the big listener next session" and, critically, "bundle + onSnapshot catch-up" should be costed as a full ~38k-read re-scan per cold boot until proven otherwise (nothing official promises bundle-resumed listens are billed as deltas). That weakens the naive form of both architectures, but it weakens **delta-watermark listeners least** when the watermark is an explicit query predicate rather than a resume token: a `where('updated','>',lastSync)` query (single-field index alone; composite once you add the `published` equality — claim 10) bills only matching docs plus a 1-read minimum, fully under your control, session gaps notwithstanding. The **static bundle + delta catch-up** design remains strong *if* the catch-up is that explicit delta query, not a listener: the bundle itself is zero client reads (claim 3), the nightly Admin build bills the corpus once server-side against the same shared 50k/day pool (claims 7, 8 — cache the artifact, build at most daily), and deletions need a reconciliation channel since bundles only merge (claim 5) — a cheap `count()` at ~1 read per 1000 docs (claim 6) is a good tripwire. Distribution favors GCS or static Hosting assets over any function-streamed authed endpoint (claim 11: 60s rewrite timeout, 10–32 MB response caps), and Hosting's 10 GB/month free egress is the binding constraint for a 50–200 MB bundle. The worker-hosted cache remains viable only in single-tab force-ownership mode, with second tabs' persistence failing hard (claim 9) — the design must tolerate that.
